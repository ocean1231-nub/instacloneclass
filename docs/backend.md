# 백엔드 개발 명세

## 기준과 수업 범위

2026년 11월 3일 화면 작업이 끝난 `frontend/src`를 기준으로 한다. 이 문서는 앞으로 연결할 서버의 명세이며, 현재 브라우저에 저장되는 데모가 서버에 구현되어 있다는 뜻은 아니다. 데이터 구조는 [database.md](database.md)를 따른다.

수업에서 서버에 연결할 기능은 회원가입·로그인, 피드와 탐색 검색, 사용자별 프로필 조회·편집, 사진 게시, 좋아요, 댓글이다. 애플리케이션 테이블은 `users`, `posts`, `likes`, `comments` 4개만 사용한다.

팔로우·게시물 저장·DM은 현재 화면에 존재하지만, 이번 수업에서는 화면 데모로 유지한다. 해당 기능의 API·서버 저장·추가 테이블은 만들지 않는다. 이 구분은 화면에서 기능을 삭제하라는 요구가 아니다.

## 구성과 저장 위치

| 역할 | 개발 중 | 배포 후 |
|---|---|---|
| API와 인증·권한 확인 | 로컬 FastAPI 서버 | 배포한 FastAPI 서버 |
| 데이터베이스 | Supabase PostgreSQL | Supabase PostgreSQL |
| 사진 파일 | Supabase Storage | Supabase Storage |
| DB 접근 | FastAPI의 SQLAlchemy 연결 | FastAPI의 SQLAlchemy 연결 |

Python 의존성과 실행 환경은 uv로 관리한다. API 접두사는 `/api`이며, 파일 업로드를 제외한 요청과 응답은 JSON을 사용한다. 브라우저는 FastAPI를 통해 데이터를 읽고 쓴다. 공개 사진만 Supabase Storage URL로 표시한다.

FastAPI는 PostgreSQL 연결 문자열로 DB에 접속하고, Storage API로 사진을 저장한다. Supabase Auth는 사용하지 않는다. 앱 회원은 `users`에서 관리하며 `auth.users`와 연결하지 않는다.

DB 연결은 실행 환경에서 지원하는 직접 연결 또는 세션 풀러를 사용하고 TLS를 적용한다. DB 비밀번호와 Storage 서버용 secret key는 FastAPI 환경 변수에만 둔다. 브라우저나 `VITE_` 환경 변수에 넣지 않는다. 연결 방식은 [Supabase PostgreSQL 연결 문서](https://supabase.com/docs/guides/database/connecting-to-postgres)를 따른다.

## 화면과 서버 기능 연결

| 현재 화면·동작 | 서버가 제공할 기능과 데이터 |
|---|---|
| 가입·로그인 모달 | 사용자 이름·비밀번호, 가입 시 이름, 로그인 사용자와 인증 토큰 |
| `/#home` 홈 피드 | 최신 게시물, 작성자·사진·문구·위치, 좋아요 수·내 좋아요 여부, 댓글 수 |
| 피드의 빠른 댓글·댓글 패널 | 같은 게시물의 댓글 목록과 댓글 작성 |
| `/#create` 게시물 작성 | 사진 한 장과 문구 등록; 미리보기는 브라우저에서 처리 |
| `/#profile` 내 프로필 | 로그인 사용자의 프로필·작성 게시물 수·작성 게시물 목록 |
| `/#user/{username}` 다른 사용자 프로필 | 주소의 사용자 이름에 해당하는 프로필·게시물 조회 |
| 프로필 편집 모달 | 표시 이름, 소개, 프로필 사진 URL 수정 |
| `/#explore` 탐색 | 게시물 격자, 사용자 이름·표시 이름 검색, 게시물 작성자 사용자 이름·문구 검색 |
| `/#reels` 릴스 미리보기 | 기존 사진 게시물 재사용; 좋아요·댓글은 같은 게시물 API 사용 |
| 설정·로그아웃 | 테마는 브라우저에 저장; 로그아웃은 토큰과 로그인 사용자 상태 제거 |

`/#…` 주소 해석과 직접 열기·새로고침 시 화면 복원은 프론트엔드 역할이다. 서버는 사용자 이름과 게시물 ID에 해당하는 데이터를 반환한다. 없는 사용자는 다른 사람의 데이터로 대체하지 않고 404로 처리한다.

## 인증과 권한

- 회원가입 시 사용자 이름 중복을 검사하고 비밀번호는 검증된 해시 라이브러리로 해시해 `password_hash`에 저장한다. 비밀번호 원문은 DB·로그·브라우저 저장소에 저장하지 않는다.
- 가입 성공 시 현재 화면 흐름에 맞춰 사용자 정보와 토큰을 함께 반환한다. 로그인도 FastAPI가 비밀번호를 검증한 뒤 만료 시간이 있는 서명된 access token을 발급한다.
- 인증 요청에는 `Authorization: Bearer <토큰>`을 사용한다. FastAPI는 서명·만료와 `users`의 사용자 존재를 확인한다. 인증·권한 확인에 Supabase Auth나 Supabase 사용자 JWT를 사용하지 않는다.
- 피드·탐색·공개 프로필·댓글 조회는 비로그인 상태에서도 가능하다. 내 프로필 조회·수정, 게시물 작성, 좋아요 추가·취소, 댓글 작성에는 로그인이 필요하다.
- 작성자와 좋아요 사용자는 토큰에서 결정한다. 클라이언트의 `author_id`나 `user_id`로 다른 사용자를 대신할 수 없다. 내 프로필 수정 대상도 토큰으로 정한다.
- 로그아웃은 클라이언트가 토큰과 사용자별 화면 상태를 지우는 방식이다. 별도 로그아웃 API·세션 테이블·토큰 갱신 기능은 두지 않는다. 발급한 토큰은 만료까지 유효하며 만료 후 다시 로그인한다.
- 비밀번호 해시와 서버 비밀값은 어떤 사용자 조회 응답에도 포함하지 않는다.

앱 테이블은 Data API에 노출하지 않는 `app` 스키마에 둔다. Data API는 비활성화하고 `anon`·`authenticated`에는 앱 테이블 접근 권한을 주지 않는다. FastAPI 전용 DB 역할에 필요한 권한만 부여하며 사용자별 허용 여부는 FastAPI가 검사한다. [Supabase 서버 직접 연결 보안 방식](https://supabase.com/docs/guides/database/secure-data)을 따른다.

## API 계약

| 메서드·경로 | 입력·동작 | 성공 응답 | 인증 |
|---|---|---|---|
| POST `/api/auth/register` | `username`, `password`, 선택 `display_name`으로 가입 | 201, `user`, `access_token`, `token_type`, `expires_in` | 불필요 |
| POST `/api/auth/login` | `username`, `password` 검증 | 200, 가입과 같은 인증 응답 | 불필요 |
| GET `/api/users/me` | 내 프로필 조회 | 200, 프로필 | 필요 |
| PATCH `/api/users/me` | `display_name`, `bio`, `avatar_url` 중 전달한 항목 수정 | 200, 갱신된 프로필 | 필요 |
| GET `/api/users` | 선택 `q`로 사용자 이름·표시 이름 검색; 없으면 사용자 목록 | 200, 공개 사용자 요약 배열 | 불필요 |
| GET `/api/users/by-username/{username}` | 해당 사용자 공개 프로필 조회 | 200, 프로필 | 불필요 |
| GET `/api/posts` | 선택 `author_id`로 작성자 필터, 선택 `q`로 작성자 사용자 이름·문구 검색 | 200, 게시물 배열 | 선택 |
| POST `/api/posts` | multipart의 `image` 한 장, 선택 `caption`으로 생성 | 201, 생성한 게시물 | 필요 |
| PUT `/api/posts/{post_id}/like` | 내 좋아요 추가; 이미 있으면 유지 | 200, `like_count`, `is_liked` | 필요 |
| DELETE `/api/posts/{post_id}/like` | 내 좋아요 취소; 없어도 성공 | 200, `like_count`, `is_liked` | 필요 |
| GET `/api/posts/{post_id}/comments` | 해당 게시물 댓글 조회 | 200, 댓글 배열 | 불필요 |
| POST `/api/posts/{post_id}/comments` | `body`로 댓글 작성 | 201, `comment`, 갱신된 `comment_count` | 필요 |

사용자 요약은 `id`, `username`, `display_name`, `avatar_url`이다. 프로필은 사용자 요약에 `bio`, `post_count`를 더한다. 프로필의 게시물 격자는 프로필 응답의 `id`로 게시물 목록을 조회한다.

게시물은 `id`, `author`(사용자 요약), `image_url`, `caption`, `location`, `created_at`, `like_count`, `comment_count`, `is_liked`를 반환한다. `is_liked`는 로그인 사용자 기준이며 비로그인 요청에는 false다. 토큰을 보냈으나 유효하지 않으면 401로 처리한다. `q`와 `author_id`가 함께 있으면 두 조건을 모두 적용한다.

댓글은 `id`, `post_id`, `author`(사용자 요약), `body`, `created_at`을 반환한다. 빠른 댓글과 댓글 패널은 동일한 API를 사용한다. 작성 이후 댓글 수와 목록을 갱신한다.

검색은 공백을 정리하고 대소문자를 구분하지 않는 부분 일치로 처리한다. 사용자 목록은 사용자 이름순, 게시물은 `created_at`·`id` 내림차순, 댓글은 `created_at`·`id` 오름차순이다. 수업용 소규모 데이터는 조건에 맞는 목록 전체를 반환하며 페이지 이동·무한 스크롤 API는 추가하지 않는다.

## 입력과 사진 처리

입력 길이·빈값·고유성은 [database.md](database.md)의 기준을 서버에서도 검증한다. 가입 시 이름이 비어 있으면 사용자 이름을 표시 이름으로 쓴다. 현재 비밀번호 화면 안내에 맞춰 최소 4자를 적용한다. 프로필 수정에서 생략한 필드는 유지하며, 빈 소개는 빈 문자열, 빈 사진 주소는 null로 처리한다. 사용자 이름 변경은 지원하지 않는다.

게시물 사진은 JPEG·PNG·WebP 한 장, 최대 5MB다. 서버는 파일 크기와 실제 이미지 형식을 검사한다. 확장자나 클라이언트가 보낸 MIME 값만 신뢰하지 않는다. 사진이 없으면 게시물을 만들지 않으며 문구는 생략할 수 있다. 위치는 현재 피드에 표시되는 선택 데이터이고, 작성 화면에는 입력란이 없으므로 신규 게시물의 `location`은 null이다.

공개 사진용 Supabase Storage 버킷 `post-images`를 사용한다. 게시물 사진은 서버가 만든 임의 파일명과 `posts/{user_id}/…` 경로로 저장한다. 공개 URL을 `posts.image_url`에 기록하며 사진 바이너리·Base64·`blob:` URL은 DB에 저장하지 않는다. 공개 사진은 URL을 아는 사람이 조회할 수 있고, 업로드·변경·삭제는 FastAPI만 수행한다. [공개 버킷의 접근 모델](https://supabase.com/docs/guides/storage/buckets/fundamentals)을 따른다.

처리 순서는 인증·입력 검사 → Storage 업로드 → DB 게시물 저장 → 성공 응답이다. 업로드 실패 시 DB 행을 만들지 않는다. DB 저장 실패 시 이번 요청이 올린 Storage 객체를 삭제한다. 정리까지 실패하면 객체 경로를 서버 로그에 남겨 수동 정리할 수 있게 한다. 게시물·사진은 서버 로컬 디스크에 영구 보관하지 않는다.

현재 프로필 편집은 사진 주소 입력 방식이다. `avatar_url` 컬럼을 그대로 유지하고, 이 프로젝트의 `post-images/avatars/` 영역에 미리 준비한 사진의 공개 HTTPS URL 또는 null을 받는다. 서버는 허용한 Storage 호스트·버킷·경로인지 검증한다. 외부 사진 자동 다운로드나 프로필 사진 파일 업로드 API는 추가하지 않는다. 기본 아바타와 학습용 샘플 사진도 Supabase Storage에 준비한다.

## 프론트엔드에 남기는 상태

- 테마, 검색어, 선택 탭, 모달, 입력 중 문구와 사진 미리보기는 브라우저 상태다. 이를 위한 DB 컬럼은 없다.
- 화면 날짜는 현재 구현대로 앱을 연 날짜를 브라우저에서 계산한다. 서버의 `created_at`은 실제 생성 시각이며 정렬에 사용한다. 앱을 연 날짜로 DB 생성 시각을 덮어쓰지 않는다.
- 작성자 이름을 이용한 사진 대체 텍스트는 화면에서 만든다. 별도 설명 입력 기능이나 DB 컬럼은 추가하지 않는다.
- 홈의 스토리 모양 버튼은 사용자 프로필 이동이다. 스토리 저장 기능을 의미하지 않는다.
- 팔로우 버튼·수, 북마크·저장 탭, DM 목록·전송은 데모로 남긴다. 계정 간 서버 동기화나 실제 메시지 전달을 이번 API가 보장하지 않는다.
- 알림·공유·게시물 메뉴·사용자 메뉴의 안내, 메시지 요청의 빈 화면, 댓글의 답글·좋아요 장식은 별도 서버 기능으로 확대하지 않는다. 온라인 표시도 실제 접속 상태 API를 요구하지 않는다.

## 오류와 환경 설정

오류 응답의 `detail`에는 화면에 표시할 설명을 담는다. 인증 실패·만료는 401, 권한 부족은 403, 없는 사용자·게시물은 404, 중복 사용자 이름은 409, 잘못된 입력은 422, 너무 큰 파일은 413, 지원하지 않는 사진 형식은 415로 처리한다. DB·Storage 연결 실패는 503으로 안내하며 비밀값·내부 오류 원문은 응답에 노출하지 않는다.

| 서버 환경 변수 | 목적 |
|---|---|
| `DATABASE_URL` | Supabase PostgreSQL 연결 문자열 |
| `SUPABASE_URL` | Supabase 프로젝트 URL |
| `SUPABASE_SECRET_KEY` | FastAPI의 Storage 접근용 서버 비밀키 |

인증 기능을 구현하는 후속 단계에서는 토큰 서명 비밀값과 유효 기간, 배포 환경의 CORS 설정도 준비해야 한다.

프론트엔드에는 API 주소만 설정한다. 개발과 배포에서 같은 종류의 Supabase 서비스를 사용하고, 연결 정보·허용 주소는 해당 환경 값으로 설정한다. 배포된 프론트엔드·API·사진은 HTTPS로 접근한다.

## 서버 연결 후 완료 확인

1. 가입 후 로그인 상태가 되고 중복 가입·잘못된 로그인·만료 토큰을 안내한다. 비밀번호 원문·해시는 응답과 브라우저 저장소에 남지 않는다.
2. 사용자별 주소로 직접 접근하거나 새로고침해도 해당 프로필과 게시물을 조회한다. 다른 사용자의 프로필은 수정할 수 없다.
3. 사진 게시 후 피드·내 프로필에 같은 게시물이 보이고, 새로고침·FastAPI 재시작·재배포 후에도 데이터와 사진이 유지된다.
4. 좋아요 추가를 반복·동시 요청해도 한 사용자·게시물 쌍에 한 행만 남는다. 취소를 반복해도 수가 음수가 되거나 다른 계정의 좋아요가 바뀌지 않는다.
5. 빠른 댓글과 댓글 패널에서 쓴 내용이 같은 목록·개수에 반영된다. 빈 댓글이나 없는 게시물에 대한 댓글은 저장되지 않는다.
6. 검색, 프로필 이름·소개·사진 URL 변경, 빈 목록 표시가 화면과 맞는다.
7. 업로드·DB 저장 실패를 성공으로 표시하지 않는다. 실패한 업로드의 사진 정리와 FastAPI를 우회한 DB·Storage 쓰기 차단을 확인한다.

## 제외한 기능과 내용

| 제외 항목 | 이유 |
|---|---|
| 게시물 삭제·수정 API와 그에 따른 사진 삭제 흐름 | 게시물 메뉴는 안내만 표시하며 삭제·수정 화면이 없음 |
| 프로필 사진 파일 업로드 API | 편집 화면은 사진 URL 입력 방식 |
| `/api/health`, 페이지 이동·무한 스크롤 확장 계획 | 현재 화면 동작을 위한 API가 아님 |
| 팔로우·북마크·DM의 서버 API·추가 테이블 | 화면 데모는 유지하되 수업의 4개 테이블 범위에서 제외 |
| 영상 업로드·재생, 스토리 게시, 알림 저장·푸시, 실제 공유 처리 | 현재는 미리보기·프로필 이동·안내만 제공 |
| 댓글 답글·댓글 좋아요, 메시지 요청 처리·실시간 통신·온라인 상태 | 동작하는 처리 흐름이 없는 표시 요소이거나 이번 수업 범위 밖 |
| SQLite 단계, DB 전환·마이그레이션 도구 도입 절차 | 개발부터 배포까지 Supabase PostgreSQL을 사용하는 수업 범위에 포함하지 않음 |
| 로컬 업로드 폴더·DB 파일·서버 영구 디스크 유지 조건 | 저장 위치를 Supabase PostgreSQL·Storage로 통일 |

현재 서버는 시작 시 테이블·버킷을 초기화하고 위의 회원, 게시물, 좋아요, 댓글, 프로필 API를 제공한다.
